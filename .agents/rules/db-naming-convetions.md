Padronização de nomenclatura para banco de dados
---

# ✅ ✔ **PADRÃO RECOMENDADO (seguido por Django, Rails, Supabase, PostgREST)**

## **1. Tudo minúsculo (`lowercase`)**

PostgreSQL converte nomes **não-aspados** automaticamente para **lowercase**.

❌ Se usar `CamelCase`, PostgreSQL exige aspas: `"MinhaTabela"`

✔ Melhor padrão:

```
usuarios
cliente_endereco
plano_execucao
```

---

## **2. Sem acentos, sem espaços, sem caracteres especiais**

Use somente:

* letras minúsculas (`a-z`)
* números (`0-9`)
* underscore (`_`)

✔ Bom:

```
resultado_execucao
tp_valor
usuario_permissao
```

❌ Ruim:

```
ResultadoExecução
resultado-execução
resultado execução
```

---

## **3. Use `snake_case`**

Sempre preferir:

```
tabela: resultado_execucao
colunas: data_criacao, id_usuario
```

Ao invés de:

```
ResultadoExecucao
DataCriacao
idUsuario
```

---

## 4. Tabelas no singular ou plural?

### A escolha moderna mais comum é **plural**:

```
usuarios
resultados
tabelas_auxiliares
execucoes
```

Por que?

* ORMs já assumem plural (`User` → `users`)
* Muitas ferramentas usam convenção plural

⚠ O importante é **consistência**.

---

## 5. Prefira prefixo `id` padronizado

Colunas de chave primária: (opção semântica)

```
id_usuario
id_plano
```

Evite:

```
usuarioID
IDUsuario
idUsuario
IdUsuario
```

---

## 6. Chaves estrangeiras: padrão recomendado

```
id_usuario  REFERENCES usuarios(id)
id_plano    REFERENCES planos(id)
```

Evita ambiguidades e facilita leitura.

---

## 7. Nome de constraints (boa prática)

### Primary key:

```
nome_tabela_pkey
```

Ex:

```
usuarios_pkey
execucao_pkey
```

### Foreign key:

```
nome_tabela_coluna_fkey
```

Ex:

```
execucao_id_usuario_fkey
execucao_id_plano_fkey
```

### Unique:

```
usuarios_email_key
```

### Check:

```
execucao_valor_chk
```

---

## 8. Nome de índices

```
<nome_tabela>_<coluna>_idx
```

Ex:

```
usuarios_email_idx
execucao_dt_coleta_idx
```

---

# ✔ RESUMO PRÁTICO (use esta regra no seu projeto)

1. **lowercase**
2. **snake_case**
3. **apenas letras, números e `_`**
4. **nomes curtos e descritivos**
5. **tabelas no plural**
6. **id como chave primária**
7. **id_<tabela> como foreign key**
8. **constraints e índices com nomes claros**
9. **ENUMs:** tipo em `snake_case`, valores em MAIÚSCULO

# 🧩 Exemplo de tabela “ideal” seguindo o padrão

```sql
CREATE TABLE public.resultados (
  id              bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  created_at      timestamptz NOT NULL DEFAULT now(),
  ds_resultado    text NOT NULL,
  dt_coleta       date NOT NULL,
  ds_comprovacao  text NOT NULL,
  id_plano        bigint NOT NULL,
  id_orgao        bigint NOT NULL,
  tp_objetivo     tp_objetivo_estrategico NOT NULL DEFAULT 'CNMP',
  tp_valor        tp_valor NOT NULL DEFAULT 'PERCENTUAL',
  valor           bigint NOT NULL DEFAULT 0,
  CONSTRAINT resultados_id_plano_fkey
    FOREIGN KEY (id_plano) REFERENCES planos(id),
  CONSTRAINT resultados_id_orgao_fkey
    FOREIGN KEY (id_orgao) REFERENCES orgaos(id)
);
```

---

# 🔥 Por que esse padrão é o mais recomendado?

* evita necessidade de aspas `"CamelCase"`
* funciona bem em ORMs
* facilita auto-geração de código
* é compatível com convenções do Supabase
* padrão universal Python / Django / Node.js / Rails
* reduz bugs em joins, migrations e views
